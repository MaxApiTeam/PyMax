PyMax 2.5.0
===========

Версия 2.5.0 добавляет FSM для диалогов, внедрение зависимостей, middleware и
составные фильтры. Расширены возможности работы с комментариями каналов,
inline-кнопками ботов и сторис. Исправлены загрузка фотографий, обработка
реакций, повторная авторизация и сохранность текста при форматировании.

Ниже перечислены пользовательские изменения относительно ``2.4.1``.

Новый публичный API
-------------------

* Добавлен FSM: ``FsmGroup`` и ``State`` объявляют шаги диалога,
  ``FSMContext`` предоставляет состояние и данные текущего пользователя в
  текущем чате. Операции доступны через ``ctx.storage``: ``get_state()``,
  ``set_state()``, ``get_data()``, ``set_data()``, ``update_data()`` и
  ``clear()``. Состояние можно ограничить TTL в секундах. Хранилище работает
  в памяти; перезапуск процесса очищает состояние и данные.
  Пример диалога: :doc:`fsm`.
* Обработчики событий могут получать дополнительные обязательные параметры
  по аннотации типа. Встроенный ``FSMContext`` автоматически передается в
  обработчик ``Message`` при наличии ID чата и отправителя. Для собственных
  зависимостей добавлена необязательная интеграция с Dishka:
  ``maxapi-python[dishka]``, ``inject()``, ``inject_router()`` и
  ``setup_dishka()``. ``auto_inject=True`` оборачивает уже зарегистрированные
  обработчики подключенных роутеров. Контейнером и его закрытием управляет
  приложение; отдельный request scope для события автоматически не создается.
  Подробнее: :doc:`di`.
* Добавлены фильтры ``Command``, ``Reply``, ``Forwarded``, ``FromMe`` и
  ``HasAttachment`` из ``pymax.filters``. Условия можно объединять операторами
  ``&``, ``|`` и ``~``. ``F.message`` и ``F.chat`` предоставляют проверки
  полей: сравнения, ``contains()``, ``startswith()``, ``endswith()``,
  ``between()``, ``is_none()`` и ``is_empty()``. Собственные фильтры наследуются
  от ``Filter`` и могут быть синхронными или асинхронными.
* ``client.add_middleware()`` регистрирует middleware для обработчиков клиента
  и подключенных роутеров. Middleware принимает ``client``, ``event`` и
  ``call_next``, выполняется после фильтров и продолжает цепочку через
  ``await call_next(event)``. Порядок входа соответствует порядку регистрации.
  Фильтры и middleware описаны в :doc:`router`.
* Для комментариев к постам каналов добавлены ``send_comment()``,
  ``fetch_comments()``, ``get_comment()``, ``get_comments()``,
  ``edit_comment()``, ``delete_comment()``, ``add_comment_reaction()`` и
  ``remove_comment_reaction()``. Методы принимают отдельно ``chat_id`` канала
  и ``post_id`` поста; ID комментария передается как ``message_id``.
* ``subscribe_comments()`` управляет подпиской на события ветки,
  ``get_comments_info()`` возвращает счетчики постов, а
  ``delete_user_comments()`` удаляет комментарии автора в ветке.
  ``set_channel_comments()`` включает или выключает комментарии канала,
  ``block_comment_author()`` блокирует авторов комментариев.
* ``Message.post_id`` сохраняет ID поста из входящего события. При наличии
  этого поля методы ``answer()``, ``reply()``, ``edit()``, ``delete()``,
  ``react()`` и ``unreact()`` работают с комментарием соответствующего поста.
  Возвращаемые из этих методов сообщения сохраняют контекст канала и поста.
  Отложенная отправка комментариев не поддерживается.
  Подробнее: :doc:`messages`.
* ``send_callback(callback_id, type, payload)`` передает нажатие inline-кнопки
  бота и возвращает ``CallbackResponse``. Результат содержит ``success`` и
  дополнительные ``message``/``chat``, если Max их прислал. Эти объекты
  поддерживают методы действий. ``ButtonType`` и ``CallbackResponse``
  доступны из ``pymax.types``.
* Inline-клавиатуры получили типизированные модели кнопок. Поле
  ``InlineKeyboardAttachment.keyboard.buttons`` содержит список строк, а
  ``callback_id`` самого вложения используется при нажатии кнопки. Данные
  конкретной кнопки доступны через ее поля: ``text``, ``type``, ``payload``,
  ``url`` и другие в зависимости от типа.
* Добавлена публикация сторис: ``send_story()`` принимает ``Photo`` или
  ``Video``, необязательную ссылку ``link`` и возвращает ``Story`` с ID.
  История публикуется на 48 часов. Для видео нужно передать положительную
  ``duration`` в миллисекундах; длительность автоматически не определяется.
* ``get_stories_feed()`` возвращает страницу превью владельцев и следующий
  курсор. ``get_stories()`` получает истории владельца, а
  ``get_stories_by_id()`` — конкретные истории по их ID.
  ``StoryPreview`` содержит владельца и счетчики; ID отдельных историй
  находятся в ``Story``. Для просмотра, изменения настроек и удаления
  доступны ``read_story()``, ``edit_story()`` и ``delete_story()``.
* ``add_story_reaction()`` и ``remove_story_reaction()`` управляют своей
  реакцией на историю. ``get_story_detailed_stats()`` возвращает страницу
  пользователей и следующий маркер. ``StoryStatsFilter.VIEWS`` выбирает
  просмотры, ``StoryStatsFilter.REACTIONS`` — реакции. Фильтр импортируется
  из ``pymax.api.stories``. Новый ``on_story_update()`` передает
  ``StoryPreview`` обновившегося владельца. Подробнее: :doc:`stories`.

Изменения поведения
-------------------

* Встроенный ``VersionCatalog`` расширен: добавлены fingerprints 16
  Android-версий Max от ``26.29.0`` до ``26.37.1`` (build ``6900``).
  Их можно выбрать через ``Client(app_version=...)`` без загрузки удаленного
  каталога. Подробнее о выборе версии: :doc:`client`.
* В каждом роутере выполняется первый подходящий обработчик данного типа
  события. После этого обход дочерних роутеров продолжается. Порядок
  регистрации теперь определяет, какой обработчик получит событие внутри
  одного роутера.
* Фильтры и обработчики сообщений одного клиента, пользователя и чата
  выполняются последовательно. Проверка состояния FSM и переход внутри
  обработчика входят в эту последовательность; сообщения с разными ключами
  могут обрабатываться параллельно.
* При reconnect того же экземпляра клиента сохраняются регистрации
  обработчиков, middleware и данные FSM. Ранее полученные ``Message``,
  ``Chat`` и ``User`` продолжают использовать текущее соединение.
  Сессия в ``InMemoryStore`` также сохраняется между reconnect, но теряется
  после завершения процесса.
* При отозванном login token автоматическая повторная авторизация выполняется
  один раз. Если новый token тоже отклонен, ``start()`` передает ошибку
  вызывающему коду. ``ExtraConfig(relogin=False)`` отключает автоматическую
  повторную авторизацию.
* Пользовательские middleware оборачивают выбранные обработчики событий.
  Внутренние уведомления о готовности файлов обрабатываются отдельно:
  пользовательская цепочка не задерживает завершение загрузки вложения.

Исправления
-----------

* Исправлен разбор сильно сжатых TCP-ответов. Корректные LZ4-ответы с
  коэффициентом сжатия больше 127 больше не отклоняются с ошибкой
  ``invalid TCP compression factor`` и не обрывают соединение. Это затрагивало,
  в частности, загрузку страниц истории сообщений.
* Загрузка фотографий поддерживает ссылки с параметрами ``photos``,
  ``photoIds`` и ссылки без ID фотографии. В последнем случае token берется
  из единственной записи ответа загрузки; пустой или неоднозначный ответ
  вызывает ``UploadError``.
* ``ReactionUpdateEvent`` принимает числовой ``message_id`` и разбирает
  счетчики из вложенного ``reactionInfo``. Поле ``your_reaction`` сохраняет
  собственную реакцию пользователя. Уведомления об изменении собственной
  реакции также направляются в ``on_reaction_update()``.
* ``on_raw`` вызывается и при ошибках распознавания, валидации или обработки
  типизированного события. Исходный frame остается доступен для диагностики.
* Markdown-форматтер сохраняет одиночные подчёркивания между буквами и
  цифрами: ссылки и идентификаторы вроде ``snake_case_name`` больше не теряют
  символы. Внутри inline-кода и блоков кода разметка, ссылки, заголовки и
  цитаты передаются буквально.
* ``CommentsInfoUpdate`` допускает ``comments_info=None`` в ответах Max.
* QR-авторизация учитывает ``ExtraConfig.password_max_attempts`` при проверке
  пароля 2FA. Пустой пароль, ошибка проверки и ответ без token учитываются
  в лимите; при его исчерпании вызывается ``PasswordAttemptsExceededError``.
* Ошибки подготовки конфигурации до создания runtime сохраняют исходный тип
  и больше не заменяются ошибкой ``Client runtime is not initialized``.
  При ошибках запуска закрываются соединение и фоновые задачи клиента.

Breaking changes и migration notes
------------------------------------

* Обычные функции и lambda больше не принимаются как фильтры роутера.
  Используйте готовые фильтры или наследуйтесь от ``Filter``. Метод
  ``__call__`` получает два аргумента — событие и клиента — и возвращает
  ``bool`` либо awaitable с результатом ``bool``. Например, прежнюю проверку
  команды можно заменить на ``@router.on_message(Command("start"))``:

  .. code-block:: python

     from pymax import Client, Message
     from pymax.filters import Filter

     client = Client(phone="+79990000000")


     class HasText(Filter[Message, Client]):
         def __call__(self, message: Message, client: Client) -> bool:
             return bool(message.text)


     @client.on_message(HasText())
     async def handle(message: Message, client: Client) -> None:
         await message.answer("Текст получен")

* Если несколько обработчиков одного роутера должны были срабатывать на
  одно событие, пересмотрите их регистрацию с учетом первого совпадения.
  Общие обработчики без фильтров размещайте после более конкретных.
* ``read_message()`` теперь принимает ``message_id`` как ``int`` для
  ``Client`` и ``WebClient``. Разделять тип ID по транспорту больше не нужно.
  ``ReactionUpdateEvent.message_id`` также имеет тип ``int``; учитывайте это
  в сравнениях и при передаче ID в собственное хранилище.
* ``InlineKeyboardAttachment.keyboard`` теперь объект ``InlineKeyboard``.
  Замените обращения вида ``attach.keyboard["buttons"]`` на
  ``attach.keyboard.buttons`` и обходите сначала строки, затем кнопки.
  Поля кнопок также доступны через атрибуты, а не ключи словаря.
* ``Message.answer()`` и ``Message.reply()`` с заполненным ``post_id``
  отправляют комментарий в соответствующую ветку. Ненулевой ``send_at``
  в этом случае вызывает ``ValueError``: планирование комментариев
  не поддерживается.
